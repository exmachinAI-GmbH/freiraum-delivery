## BEF-C1 · Die Migration ist nicht wiederholbar — **schwer**

### Was gemessen wurde

```
psql:migrations/260802_anmeldecode.sql:65: ERROR:  relation "login_code" already exists
```

Der CI-Schritt *„Zweiter Lauf ändert Schema UND Daten nicht"* spielt die Migration ein
zweites Mal gegen dieselbe frische Datenbank ein. Sie bricht sofort ab.

### Warum das zählt

**M1 des Bauauftrags** verlangt wörtlich: *„Die Datenbank steht. Die Sammelmigration ist im
Zielbestand eingespielt; **ein zweiter Lauf ändert nichts**."* Und Tor I, Bedingung 4:
*„Migration zweimal, **Schema und Daten** danach gleich."*

Der N2-Lauf vom 06.08. hat das für **M30** nachgewiesen — beide Diffs leer. Für
`260802_anmeldecode.sql` ist es **nie** geprüft worden. Sie ist am 02.08. gegen eine leere
Datenbank gelaufen und danach nicht wiederholt.

> **Das ist derselbe Befundtyp wie MB-4.** Die Läufe vom 5.8. waren grün, weil das Konto
> Superuser war; die Migration wäre auf Azure vollständig gescheitert. Hier ist es dasselbe
> Muster: grün beim ersten Lauf, unbrauchbar beim zweiten. *„Ausführen schlägt Lesen."*

### Was zu tun ist

**Neun Anweisungen sind nicht abgesichert.** Alle in `migrations/260802_anmeldecode.sql`:

| Zeile | Anweisung | Absicherung |
|---|---|---|
| 40 | `CREATE TABLE login_code (…)` | `CREATE TABLE IF NOT EXISTS` |
| 70 | `CREATE INDEX login_code_actor_idx` | `CREATE INDEX IF NOT EXISTS` |
| 74 | `CREATE UNIQUE INDEX login_code_nur_einer_offen` | `CREATE UNIQUE INDEX IF NOT EXISTS` |
| 81 | `CREATE FUNCTION login_code_entwertet_aeltere()` | `CREATE OR REPLACE FUNCTION` |
| 93 | `CREATE TRIGGER login_code_entwertet_aeltere_trg` | **kein `IF NOT EXISTS` in PostgreSQL 16** — siehe Muster unten |
| 104 | `CREATE TYPE mail_kind AS ENUM (…)` | **kein `IF NOT EXISTS`** — siehe Muster unten |
| 105 | `CREATE TYPE mail_status AS ENUM (…)` | dito |
| 107 | `CREATE TABLE mail_delivery (…)` | `CREATE TABLE IF NOT EXISTS` |
| 127 | `CREATE INDEX mail_delivery_actor_idx` | `CREATE INDEX IF NOT EXISTS` |

`COMMENT ON` (Z. 67, 123) ist bereits wiederholbar — dort ist nichts zu tun.

**Für Typ und Auslöser gibt es ein Hausmuster.** M30 verwendet es bereits, etwa bei
`tv_merkmale_ganz` (`M30__pilot_sammelmigration.sql`:627–634):

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'mail_kind') THEN
    CREATE TYPE mail_kind AS ENUM ('EINLADUNG','ANMELDECODE');
  END IF;
END $$;

DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_trigger
                 WHERE tgname = 'login_code_entwertet_aeltere_trg') THEN
    CREATE TRIGGER login_code_entwertet_aeltere_trg …;
  END IF;
END $$;
```

**Nicht** mit `DROP … IF EXISTS` davor arbeiten. Ein `DROP TYPE` scheitert an abhängigen
Spalten, ein `DROP TRIGGER` mit anschließendem `CREATE` ist beim zweiten Lauf zwar
wirkungsgleich, hinterlässt aber einen Moment ohne Wächter — und das ist bei einem
Freigabewächter kein akzeptabler Zustand.

### Wie der Nachweis aussieht

```
1. gegen eine FRISCHE Datenbank einspielen
2. Schemadump nehmen
3. NOCHMAL einspielen        ← muss ohne Fehler durchlaufen
4. Schemadump nehmen
5. beide Dumps vergleichen   ← muss leer sein
6. dasselbe für die DATEN, nicht nur das Schema (Tor I Nr. 4)
```

Der CI-Schritt tut das bereits — es genügt, den Pull Request neu laufen zu lassen. **Kein
eigener Nachweis nötig**, das Gate ist der Nachweis.

## BEF-C2 · Zwanzig Stil-Befunde in `mail/versand.py` — **leicht**

### Was gemessen wurde

`ruff` meldet 20 Befunde, **alle in `mail/versand.py`**:

| Anzahl | Kennung | Was |
|---|---|---|
| 11 | `UP031` | Prozent-Formatierung statt Format-Bezeichner |
| 3 | `F401` | ungenutzte Importe — `datetime`, `timedelta`, `timezone` |
| 2 | `BLE001` | `except Exception` ohne Einschränkung |
| 2 | `EXE001` | Shebang vorhanden, Datei aber nicht ausführbar |
| 1 | `UP009` | überflüssige Kodierungszeile |
| 1 | `PIE808` | überflüssiges `start`-Argument in `range` |

### Was zu tun ist

Neun der zwanzig sind maschinell behebbar:

```
ruff check --fix mail/versand.py     # F401, UP009, PIE808 und ein Teil von UP031
chmod +x mail/versand.py             # EXE001
```

**Die beiden `BLE001` gehören angesehen, nicht weggemacht.** `except Exception` fängt in
`versand.py` den Versandfehler und schreibt ihn als Zustellnachweis mit Status `FEHLER`
(Z. 137, Z. 165). Das ist an dieser Stelle **richtig** — ein Versandfehler darf den Lauf nicht
abbrechen. Zwei Wege:

- die Ausnahme auf `smtplib.SMTPException` und `OSError` verengen, oder
- `except Exception` behalten und mit `# noqa: BLE001` samt einzeiliger Begründung versehen.

**Nicht** die Regel im Prüfwerkzeug abschalten. K23-D05: *„Ein Prüfwert DARF NICHT gesenkt
werden, damit ein Lauf besteht."*
