## BEF-G1 · Die Vergabe der Kunden-Codes ist überhaupt nicht gebaut — **offen**

> **Kurz:** Keine einzige Zeile im Programmtext vergibt einen Kunden-Code. Der Befund ist
> **größer als B1-F2**, und eine neue Bedingung in der Datenbank schließt ihn nicht.

### Was verlangt ist — K02-M25 im Wortlaut

> **K02-M25** · Der Kunden-Code MUSS fortlaufend von der Plattform vergeben werden. Der erste
> lautet `DE-AAA`; jeder weitere ist der nächste freie Code der alphabetischen Folge.

*(Quelle: `03_KONZEPTE_v2.9/concepts-md/260801_FREIRAUM_K02_Fundament_v1.3.md`, Zeile 293.
Wortgleich im Klauselregister dieses Repos.)*

Drei weitere MUSS-Klauseln hängen unmittelbar daran:

> **K02-M26** · Die Vergabe MUSS serverseitig und in derselben Transaktion wie die Anlage des
> Mandanten erfolgen. Schlägt sie fehl, entsteht kein Mandant. *(Zeile 294)*
>
> **K02-M27** · Die Vergabe MUSS jeden Code überspringen, dessen erster Buchstabe `Z` ist. Der
> Namensraum `DE-Z..` wird von der fortlaufenden Vergabe nie erreicht. *(Zeile 295)*
>
> **K02-M28** · Ist außerhalb des reservierten Namensraums kein freier Code mehr vorhanden,
> MUSS die Anlage abgelehnt werden. Ein Ausweichen in den reservierten Namensraum findet nicht
> statt. *(Zeile 296)*

Und ein DARF-NICHT, das dieselbe Sache von der anderen Seite sagt:

> **K02-D10** · Der Kunden-Code DARF NICHT eingegeben, gewählt oder aus dem Namen des Mandanten

**Zusammen genommen heißt das:** Der Code entsteht **im Server**, **beim Anlegen**, **aus einer
Folge**, **mit einer Sperrzone**, **und mit einem Abbruch am Ende der Folge.** Fünf Aussagen,
die zusammen einen Vorgang beschreiben — keine Datenbankspalte.

**Lesen tut den Code niemand.** Kein `SELECT`, keine Anzeige, keine Weiterverwendung. Das
zählt: **K01-M35** verlangt, dass die drei Großbuchstaben einer Projektnummer *genau* der
Kunden-Code des tragenden Mandanten sind. Wer den Code nicht liest, kann diese Klausel nicht
erfüllen.

**Setzen tut ihn nur die Prüfung — von Hand.** Alle **18** setzenden Stellen (13 in den
Startbeständen der Prüfung, 4 in den Negativfällen der Migration, 1 in `pruefe_b1.sh`) tragen
einen ausgedachten Code ein. Keine davon rechnet einen aus. Der Bau selbst tut es nirgends.

### Warum der Befund größer ist als B1-F2

B1-F2 ist eine **fehlende Schranke** an einem vorhandenen Feld: der Code lässt sich an einen
Nicht-Kunden hängen. Der Bereich dahinter ist gebaut, nur ungeschützt.

Hier fehlt der **Vorgang selbst**. Das ist ein Unterschied in der Art, nicht im Grad:

| | B1-F2 | BEF-G1 |
|---|---|---|
| Was fehlt | eine Bedingung | ein Serverbefehl mit Folgenlogik, Sperrzone und Abbruch |
| Betroffene Klauseln | K02-G02 (GILT) | **K02-M25 · M26 · M27 · M28 · D10** — fünf, davon vier MUSS |
| Gegenmittel | eine Zeile in einer Migration | ein gebauter, geprüfter Weg |
| Wirkung heute | ein Code kann falsch sitzen | **es entsteht kein Code** |

**17 Klauseln des gezeichneten Bestandes sprechen vom Kunden-Code** (gemessen im
Klauselregister, Suche über den Wortlaut nach *Kunden-Code*, *DE-AAA*, *DE-Z..*,
*Namensraum*, *customer_code*); mit K02-M26 und K02-G16, die den Begriff umschreiben statt
ihn zu nennen, sind es **19**. Für **keine** von ihnen führt das Register ein
Akzeptanzkriterium oder einen Test:

```
K02-M25 | herkunft: …K02_Fundament_v1.3.md:293 | test: '' | ergebnis: '' | kritikalitaet: ''
K02-M26 | herkunft: …K02_Fundament_v1.3.md:294 | test: '' | ergebnis: '' | kritikalitaet: ''
```

### Warum eine neue Datenbankbedingung ihn nicht schließt

Die in B1-F2 vorgeschlagene Bedingung lautet:

```sql
CHECK (customer_code IS NULL OR kind = 'CUSTOMER')
```

Sie **verbietet**, dass ein Code am falschen Mandanten sitzt. Sie **erzeugt keinen**. Nach
ihrer Einführung gilt unverändert:

- Kein Weg rechnet den nächsten freien Code aus (**K02-M25** nicht erfüllt).
- Keine Transaktion verbindet Vergabe und Anlage (**K02-M26** nicht erfüllt).
- Nichts überspringt den Namensraum `DE-Z..` (**K02-M27** nicht erfüllt).
- Nichts lehnt die Anlage ab, wenn die Folge erschöpft ist (**K02-M28** nicht erfüllt).

Schlimmer: die Bedingung **verschärft** die Lage kurzfristig. Sie macht `customer_needs_code`
zur harten Sperre in beide Richtungen. Ein Kundenmandant kann dann ohne vergebenen Code
**gar nicht mehr angelegt werden** — und einen vergebenden Weg gibt es nicht. Wer nur die
Bedingung einführt, tauscht einen stillen Fehler gegen einen lauten Stillstand.

**Das ist kein Argument gegen die Bedingung.** Es ist ein Argument dafür, sie **zusammen mit
dem Vergabeweg** zu bauen, nicht davor.

### Was hier offen bleibt

| | Offener Punkt | Wer entscheidet |
|---|---|---|
| 1 | Ob der Vergabeweg in den Umfang bis zum 31.08.2026 gehört | **Auftraggeber**. Am 15.08. ist für B1-F2 Weg a entschieden (siehe BEF-G2); für die Vergabe selbst ist **keine Entscheidung belegt** |
| 2 | Ob die Folge `DE-AAA → DE-AAB → …` oder `DE-AAA → DE-ABA → …` läuft | **Konzept-Fabrik**. K02-M25 sagt *„der nächste freie Code der alphabetischen Folge"* — das legt die Reihenfolge nicht eindeutig fest |
| 3 | Wie sich *„der nächste **freie**"* zu K02-D06 verhält, wenn ein Code irrtümlich vergeben wurde | **Konzept-Fabrik**. K02-D06 verbietet die Änderung eines vergebenen Codes; ob das Zurücknehmen einer irrtümlichen Vergabe eine Änderung ist, sagt keine Klausel |

**Dieses Blatt entscheidet keinen der drei Punkte.** Es legt sie vor.

### Der schwerere Teil: Das Prüfskript der Installation erzeugt den Schaden selbst

**Die Zeile ist `install/pruefe_b1.sh:29.** Sie steht im Negativfall der Zeilen 28 bis 30:

```bash
28  neg "Kunden-Code am Betreiber-Mandanten wird abgewiesen" \
29    "UPDATE tenant SET customer_code='DE-AAA' WHERE kind='OPERATOR';" \
30    "ERROR"
```

Der Fall trägt im Titel die Behauptung *„wird abgewiesen"*. Er wird nicht abgewiesen. Und die
Hilfsfunktion `neg` (Zeilen 4 bis 11) ruft `psql` mit einem einzelnen `-c` auf — **ohne
Transaktionsklammer**. Was durchläuft, ist geschrieben und bleibt geschrieben. Im ganzen
Skript (42 Zeilen) steht kein `ROLLBACK`, kein Zurücksetzen, kein Aufräumen.

**Nachgemessen, nicht behauptet.** In einer eigens angelegten Wegwerf-Datenbank
(`bef_g_probe`, Grundschema + Vorläufermigration + M30 + `install/01_betreiber_und_erstadmin.sql`,
nach der Messung wieder entfernt) wurde die Funktion `neg` wortgleich übernommen und der Fall
aus Zeile 28–30 gefahren:

```
Zustand vor dem Negativfall
   kind   |      name       | customer_code
----------+-----------------+---------------
 OPERATOR | exmachinAI GmbH |

  FEHLGESCHLAGEN  Kunden-Code am Betreiber-Mandanten wird abgewiesen — DURCHGELAUFEN

Zustand NACH dem Negativfall
   kind   |      name       | customer_code
----------+-----------------+---------------
 OPERATOR | exmachinAI GmbH | DE-AAA
```

**Der Betreiber-Mandant trägt jetzt `DE-AAA`.** Genau den Code, der nach K02-M25 dem ersten
echten Kunden zusteht. Die Folge, ebenfalls gemessen:

```
$ psql -c "INSERT INTO tenant (kind,name,customer_code,legal_space,avv_datum,avv_aktenzeichen)
           VALUES ('CUSTOMER','Erster echter Kunde','DE-AAA','DE',DATE '2026-08-15','AZ-0001');"

ERROR:  duplicate key value violates unique constraint "tenant_customer_code_key"
DETAIL:  Key (customer_code)=(DE-AAA) already exists.
```

**Der erste echte Kunde bekommt seinen Code nicht mehr.** Das Prüfskript hat ihn verbraucht.

### Drei Dinge, die daran zusammenkommen

**1 · Das Skript meldet ehrlich — und richtet trotzdem an.** Es schreibt `FEHLGESCHLAGEN … 
DURCHGELAUFEN`. Wer hinsieht, erfährt es. Aber die Meldung kommt **nach** dem Schreibvorgang,
und niemand nimmt ihn zurück. Ein Negativfall, der seinen eigenen Gegenstand herstellt, ist
kein Nachweis, sondern eine Ursache.

**2 · Der erwartete Grund ist `ERROR`, nicht eine benannte Bedingung.** Die anderen Fälle
desselben Skripts erwarten `actor_sealed_no_money` oder einen Meldungswortlaut. Dieser erwartet
die Zeichenfolge `ERROR` — **jeden** Fehler. Sobald die Bedingung aus B1-F2 eingeführt wird,
meldet der Fall `OK`, gleichgültig woran er scheitert: an der neuen Bedingung, an
`customer_code_fmt`, an einem Tippfehler. **Das ist wortgleich der Fehler aus B1-F1** vom
02.08.2026 und aus **BEF-M3-6** vom 15.08.2026: geprüft wird, *dass* etwas scheitert, nicht,
*an welcher Bedingung*. Er wird also mit der Behebung nicht verschwinden, sondern unsichtbar.

**3 · Die Kennzeichnung ist unterwegs verloren gegangen.** `BEF-C_260807.md`, Abschnitt
*„Ein dritter Punkt, der nicht Tor 1 ist"*, hält fest, die damals nicht eingecheckte Änderung
an `install/pruefe_b1.sh` sei *„als bekannter offener Befund gekennzeichnet"*. In der heute
eingecheckten Fassung steht **keine solche Kennzeichnung** — kein Kommentar, kein Verweis auf
B1-F2. Gemessen: `grep -n "B1-F2" install/pruefe_b1.sh` → kein Treffer.

### Was zu tun ist — und was ausdrücklich nicht

| | | Wer |
|---|---|---|
| **Nicht** | Die Bedingung aus B1-F2 jetzt einführen. Der Auftraggeber hat am 15.08. Weg a entschieden; außerdem stünde sie ohne den Vergabeweg allein da (BEF-G1) | — |
| **Ja** | Den Negativfall in `install/pruefe_b1.sh` **kenntlich machen**: Verweis auf B1-F2 und RR-03 in den Fallnamen, damit niemand die Meldung für einen Bruch von heute hält | Bau, `install/` — **nicht dieses Blatt**, es schreibt nur in `nachweise/` |

**Ein Hinweis für den Pilotstand.** Ob `install/pruefe_b1.sh` je gegen den laufenden
Pilotstand gefahren wurde und dort `DE-AAA` am Betreiber-Mandanten hinterlassen hat, ist von
diesem Blatt aus **nicht belegt** — der Pilotstand wurde für diese Messung bewusst nicht
angefasst. Die Prüfung ist ein Einzeiler:

```sql
SELECT kind, name, customer_code FROM tenant WHERE customer_code IS NOT NULL AND kind <> 'CUSTOMER';
```

Liefert sie eine Zeile, ist der Code verbraucht — und K02-D06 (*„Der Kunden-Code DARF NICHT
geändert werden, sobald er vergeben ist"*) macht das Aufräumen zu einer Frage, die keine
Klausel beantwortet. Sie steht als offener Punkt 3 in BEF-G1.
